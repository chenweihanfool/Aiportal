# 入口網全面檢視與重新設計（2026-10）

> 起因（使用者原話）：「幫我重新對入口網做全面檢視 重新設計或重構 對齊我的目標。入口網的卡片與指標是歷來陸續加上的，從沒做過一次整體資訊架構檢視——什麼該上首頁、什麼該收進抽屜、該畫什麼圖、顯示哪些指標，目前沒有統一標準。我的目標是 串接我所有子系統 人生進度 運動追蹤 任務系統 vps上的Hermes知識庫管線 把重要指標用具現代感 有趣的方式顯示出來 做為我長期性 具成長性 陪伴我的窗口。知識庫系統也幫我審視 目前架構長期來看能否達到我的目標。另外 我想入口網新增美食地圖 幫我把知識庫中記錄的想吃美食做UI介面出來 不知道adventurelog是否能整合？」
>
> 範圍：Aiportal（入口網）、kb-pipeline（知識庫管線），並對照 FitnessForge、pf-cwh 的對外摘要介面。依據是 2026-10-15 各 repo 的程式碼與文件（分支 `claude/portal-redesign-audit-ndaerw`，Aiportal v2.32.0）。**我碰不到 `/vault` 與正式環境**，凡是需要實機資料才能確認的，都標「推斷」或「未驗證」。
>
> 標 **【需決定】** 的項目要使用者裁定，裁定前不動手。

## 0. 一頁結論

1. **入口網現在是「維運儀表板」，還不是「人生陪伴窗口」**。首頁 6 張卡裡，3 張在看 HERMES 自己（關係網路、管線、主機），1 張看 Ollama 帳單，只有幸福指數與想法庫在看「你」。四個子系統（人生進度、運動、任務、旅遊）只剩幸福指數卡上的一列分數，細節收在第二層抽屜。
2. **新首頁架構：「今天 → 六個面向 → 成長 → 好玩的 → 系統一顆燈」五段**（§2.6）。HERMES 的維運資訊收成一顆「系統燈號」，點開才是現在的戰情室。首頁改放六個生活面向的小卡（各帶 30 天趨勢）、長期成長軌跡（年度進度、知識庫累積、里程碑），以及想法庫與美食地圖這兩個「有趣」的入口。
3. **知識庫評級：B−**。萃取管線本身工程扎實：防幻覺的機械閘、失敗班次能被看見、成本有在量測、文件與測試完整（69 個測試檔）。但要當「長期、可成長的知識底座」，有三個結構性風險：
   - **R1 資料模型只寫在 prompt 裡，每多一種資料就要多一支 pusher、一張表、一個端點**；
   - **R2 正式知識靠 LLM agent 直接寫檔，而且執行環境分散在 VPS、NAS、家中 Windows 三處**；
   - **R3 沒有查詢層**，知識只能經 Obsidian 或入口網的整包圖譜推送去用。
   另外，**L1 明文「不抽地點」**，所以美食和旅遊這類以地點為主的知識，現在無法從管線自然長出來（§3）。
4. **美食地圖**：程式碼與文件裡**找不到任何「想吃美食」的紀錄格式**（kb-pipeline 全庫搜尋「美食／想吃／餐廳／food」0 筆）。推斷目前只散落在日記的自由文字裡，或被 L1 當成一般事件處理。建議比照想法庫，新增日記格式 `### HH:MM 🍜 店名`，用確定性程式萃取、推上入口網（§4）。本次已在入口網做好**示範資料的 UI 原型**（`#food`，見 §6）。
5. **AdventureLog 建議：「借用概念＋選配單向同步」，不當美食資料的主要來源**。你家裡已經有一台 AdventureLog（NAS 上的 `adventure.cwh2023.synology.me`），入口網的「旅遊生活」維度也已經在讀它的 `/api/visits/`。但它沒有「想吃」的語意（想吃的理由、誰推薦、必點），資料不在知識庫、不能回溯日記，跨機器雙向同步的成本也高。建議分工：知識庫是權威來源，入口網自建美食地圖；「去過」的店家可選擇單向寫進 AdventureLog 的「美食」類別，讓旅遊地圖看得到（§4.5）。

## 2. 資訊架構標準

### 2.1 三層原則

| 層 | 回答的問題 | 看的頻率 | 放什麼 | 不放什麼 |
|---|---|---|---|---|
| **L0 首頁** | 「我今天好嗎？有什麼要注意？有什麼值得期待？」 | 每天 | 每個面向**一個主數字＋一條趨勢＋一句話**；異常（紅）；可以立刻做的事 | 算式、維運細節、全綠的系統狀態 |
| **L1 抽屜** | 「為什麼是這個數字？」 | 每週 | 拆解、歷史、比較、篩選清單 | 要去原系統才能改的操作 |
| **L2 原系統／全頁** | 「我要怎麼改變它？」 | 需要時 | pf-cwh、FitnessForge、Vikunja、AdventureLog、Obsidian、關係宇宙、時間軸、美食地圖 | — |

**上首頁的條件（全部成立）**：
1. 和「你本人」有關（不是 HERMES 自己的健康），**或者**是出了需要你處理的異常。
2. 每天看會不一樣（日頻以上），或者有明確的期待感（倒數、下一家想吃的店）。
3. 能用一個數字或一句話說完，不用讀算式。
4. 首頁上同一個量只出現一次。

**收進抽屜的條件（任一成立）**：解釋性內容（算式、權重、原始值與百分位）、清單（全部想法、全部店家）、維運資訊（全綠時）、低頻（月、季）。

**系統資訊的升降規則**：平常收成一顆「系統燈號」；任何一項是 warn 或 crit 時，燈號上首頁並寫出「哪一項、多久了」（例如「管線 L3 昨晚失敗」「硬碟約 21 天後寫滿」「Ollama 會在補點前用完」）。

### 2.2 指標類型對應圖表

| 指標類型 | 例子 | 首頁畫法 | 抽屜畫法 | 不要用 |
|---|---|---|---|---|
| 綜合分數 0–100 | 幸福指數 | 環形＋等級字＋30 天迷你線 | 雷達（各面向）＋趨勢線＋洞察 | 只有數字沒有趨勢 |
| 面向分數（百分位） | 六維度 | 小卡：數字＋7/30 天迷你線＋▲▼ | 原始值與百分位並列、算式、子指標長條 | 儀表盤（6 個儀表很佔空間，看不出趨勢） |
| 累積量（只增不減） | 人物數、事件數、想法數、去過幾家 | 大數字＋「本週 +n」 | 面積圖（累積曲線） | 百分比 |
| 比率／進度 | 年度進度、休假配速、實現率 | 進度條（標出「應有進度」刻度） | 進度條＋歷史 | 圓餅 |
| 頻率／節奏 | 每週運動次數、日記篇數、新想法 | 近 8–12 週長條 | 日曆熱圖（GitHub 式，一年） | 折線（離散事件用長條或熱圖） |
| 構成 | 肌群、硬碟分項、模型分佈 | 不上首頁 | 橫向長條（排序）；雷達只用在固定軸（肌群） | 圓餅超過 4 塊 |
| 預測 | 硬碟寫滿、Ollama 用完 | 一句話＋日期（異常才上首頁） | 實線歷史＋虛線預測 | 只給天數不給日期 |
| 地點 | 美食、旅遊 | 「下一家」＋小地圖縮圖 | 地圖＋清單 | 只有清單 |
| 關係 | 人事網路 | 不上首頁（只放累積數字） | 關係宇宙全頁 | — |
| 狀態 | 管線、容器、推送 | 一顆燈（合併） | 表格，每列一燈 | 首頁逐項列出 |

### 2.3 命名與單位

- **指標名稱**：用「生活語言名詞」，不用演算法名稱。首頁寫「從容」不寫「忙碌指數反轉」；寫「財務自由」不寫「lifeFreedomScore」。同一個量全站只用一個名字，例如「心智分數」不能同時叫「心智指標」，「人生自由」和「人生進度」也要統一。【需決定】名稱表（建議見 §2.6 的六面向）。
- **分數**：0–100 整數，首頁不帶小數；抽屜才顯示一位小數。百分位要標「近 90 天百分位」，原始值要標「原始值」，兩者不放在同一個大數字位置。
- **金額**：台幣寫 `NT$ 1,234,567`（千分位，首頁可以縮寫成 `NT$ 123.4 萬`）；美元寫 `$12.34`。
- **百分比**：`12%`（整數）；報酬率帶正負號：`+5.2%`。
- **時間**：絕對日期一律用台北時間 `YYYY-MM-DD` 或 `10/15`；相對時間「3 分鐘前、5 小時前、2 天前」（沿用 `minutesAgo`，全站統一一個函式）。
- **天數**：「21 天後（11/05）」——預測一定同時給天數和日期。
- **趨勢符號**：`▲ 3`（變好）、`▼ 3`（變差），顏色依「變好或變差」決定，不依數值正負（例如逾期變少是好事，要用綠色）。

### 2.4 空狀態與過期資料（統一狀態機）

每張卡、每個指標都只會處於以下其中一種狀態，前端用同一個元件呈現：

| 狀態 | 條件 | 呈現 |
|---|---|---|
| `locked` | 未解鎖 | 卡片外框保留、內容模糊，寫「解鎖後顯示」 |
| `loading` | 請求中 | 骨架（灰條），不寫「載入中…」文字 |
| `pending` | 系統剛上線、資料還不夠（例如歷史 < 2 天） | 「資料累積中：再 n 天會畫出趨勢」，**不顯示 0** |
| `empty` | 真的是 0（例如本週沒運動） | 顯示 0，並寫「這是真的 0」以及一個行動提示 |
| `fresh` | `now - updatedAt ≤ 1.5 × 預期間隔` | 正常 |
| `stale` | `1.5× < 經過時間 ≤ 3×`，日更資料是 36 小時 | 數字照常顯示，但淡化 55%，右上加「n 小時前的資料」徽章 |
| `dead` | 超過 3× 預期間隔，日更資料是 72 小時 | 數字換成「—」，寫「已 n 天沒有更新：<來源>」，並上首頁的系統燈 |
| `error` | 請求失敗 | 保留上一次的值（標 stale），失敗原因放 tooltip |

- 每種資料都要宣告 `expectedEveryMin`。推送端（`pusherHealth`）已經有這個欄位，前端應共用同一張表，不要每張卡各寫一套（現在有 36 小時、30 分鐘、「資料已過期」三套寫法）。
- 「今日暫定」（幸福指數 23:55 前）是一種 `fresh` 的子標記，不是過期。

### 2.5 顏色語意（沿用 theme.ts）

- 琥珀 `amber` 只用來表示「重點、可互動」，不用來表示狀態。
- 狀態只用 `ok`／`warn`／`concern`／`crit`／`steelDim`（無資料）。
- 六面向各配一個**識別色**（新增；首頁小卡、雷達、時間軸共用），讓使用者用顏色認出面向：財務＝金、身體＝青綠、從容＝藍、心智＝紫、社交＝珊瑚、旅遊與美食＝橘。【需決定】是否引入識別色（會讓深色儀表板風格變得比較「活」）。

## 3. 知識庫審視（kb-pipeline）

### 3.1 架構速寫（依 `docs/pipeline-architecture.md`、`schedules/jobs-index.md`、腳本）

- **資料模型**：Obsidian vault（Markdown＋YAML frontmatter）。正式實體有 `Events/`、`People/`、`Cases/`、`Objects/`，另有概念、方法（`AI/知識`、abstractions ledger）、`Ideas/`、`社交/social_interactions.jsonl`。運行狀態放在 `pipeline/state/*.json`（例如 `ideas.json`、`.l3-landed-ids.json`）。
- **攝取**：
  - 日記增量走 L1（候選）→ L2（消歧、合併）→ L3（唯一可寫正式檔）→ L5（敘事）；
  - RAW 文件走 L4（OCR）；
  - 歷史涓滴；
  - NAS 拉檔（home-pull）。
- **去重**：L3 ledger 跨日去重、L2 名稱語意沿用、ideas 相似度 0.85、`append-candidate-queue` 機械閘（人名必須逐字出現在日記裡）。
- **查詢**：沒有專用查詢層。使用方式只有 Obsidian 閱讀、入口網關係圖（整包推送）、時間軸、事件內文推送。
- **備援**：
  - vault 在 git 裡（`git-vault-commit.py`，L1/L2/L3 前後快照）；
  - Hermes `state.db` 每週日 05:30 備份；
  - Postgres 每天 04:50 備份；
  - Syncthing 單向送到 NAS（有版本保留）。
- **維運**：jobs.json 共 34 個 job（啟用約 24 個，agent 型約 14 個），69 個測試檔，`[CRON_FAILURE]` 偵測、L3 自動降載、portal-sync、推送健康表、排程 prompt 每日鏡像。
- **與入口網的介面**：11 種 push feed，每種有一支 pusher、一個 `/admin/*` 端點和一張表；入口網不能反向寫入（想法庫、美食都用「複製一句話給 HERMES」）。

### 3.2 評分

| 面向 | 評分 | 依據 |
|---|---|---|
| 攝取與萃取品質 | **A−** | 防幻覺機械閘、evidence 逐字比對（ideas backfill）、失敗班次看得見、自動降載與補跑 |
| 資料模型與 schema | **C** | schema 散在 prompt 與 wrapper 裡（例如 `object_type` 的枚舉只寫在 L1 prompt 字串），沒有可驗證的 schema 檔與版本號；**地點不是實體**（L1：「不抽地點、不抽時間」） |
| 去重與一致性 | **B+** | ledger＋語意沿用＋相似度；名稱合併保留原措辭、可拆回 |
| 查詢與可用性 | **D** | 沒有索引、沒有查詢 API；入口網只能拿到推送端預先算好的整包 |
| 可擴充性（新增一種資料） | **C** | 想法庫這次新增，從萃取器、state、Obsidian 頁、pusher、端點、資料表、型別到卡片，橫跨 2 個 repo 約 10 個檔案；美食會重來一次 |
| 備援與可回滾 | **B** | 備份齊全且有驗證設計；但還原演練沒有排程化，vault 的 git 鎖註解寫「local NTFS file lock」（推斷是 Windows 時代的遺留，未驗證 VPS 上的行為） |
| 可遷移性 | **C+** | 時區靠環境變數 `TZ`；路徑集中在 `kbcore/config.py`（好）；但仍有家中 Windows 路徑（`sync-diary-to-adventurelog.py` 的 `TOKEN_SRC`、`STATE_PATH`）、NAS 與 VPS 雙向依賴 |
| 維運成本 | **B−** | 成本有量測（cron-usage-summary），也有減量；但約 4 成班次的 token 量測不到（claude-code provider），排程數量偏多 |
| 文件與治理 | **A−** | project-goals、決策先例表、各機制文件都完整；但 `pipeline-architecture.md` 的排程表已經過時（寫 L1 10:30/16:30/20:30、L3 22:40、L5 00:00、L4 08:15/14:15；實機是 L1 10:30/20:30、L3 00:10、L5 02:00、L4 11:35/17:35），另外 workload-halving 寫「L1 維持每天 3 班」，jobs-index 是每天 2 班 |

**總評 B−**：作為「把日記變成結構化知識」的萃取器，品質已經不錯；作為「陪伴十年、會長大的個人知識底座＋入口網的資料來源」，資料模型、查詢層和擴充成本是瓶頸。

### 3.3 前三大風險

**R1　schema 隱含＋點對點推送，擴充成本線性增加**
- 現象：實體欄位寫在 prompt 和 wrapper 字串裡；每多一種資料就多一支 pusher、一個端點、一張表、一套前端型別（目前 11 種）。
- 後果：五年後新增面向的成本越來越高；prompt 一改欄位就可能悄悄漂移；入口網和管線的契約只靠雙方程式碼「剛好一致」。
- 改進：
  - 定一份 `schemas/`（JSON Schema 或 pydantic），涵蓋 Event、Person、Case、Object、Idea、Food（新）、Place（新）與 feed payload，給版本號，兩邊都拿它驗證；
  - 新 feed 改走**一個泛用端點** `POST /api/admin/feed/:name`（`{schemaVersion, generatedAt, payload}`），存進一張 `feed_snapshot(name, version, payload jsonb, received_at)` 表，前端用 §2.6 的註冊表讀；
  - 既有 11 種不急著搬，新的（美食、地點）先走這條。

**R2　正式知識由 LLM agent 直接寫檔；執行環境分散在三處**
- 現象：L3 agent 依 wrapper 指示 `write_file`、`patch` 正式檔；曾撞上限半途而廢（10/01、10/02）；約 4 成班次成本量測不到。旅遊同步依賴家中 Windows 路徑；token 用正規式從另一支腳本原始碼讀取；home-pull 從 NAS 拉到 VPS。
- 後果：可驗證性和可遷移性受限；換機器或 Windows 關機時會靜默失效；token 有外洩風險。
- 改進：
  - 正式檔寫入改由確定性腳本執行：agent 只產出經 schema 驗證的 YAML，`l3-apply.py` 落地。現在已有 normalized 佇列閘口，把「寫正式檔」也收進同一道閘；
  - `sync-diary-to-adventurelog.py` 的 token 改用 `kbcore.config.load_env_key('ADVENTURELOG_API_TOKEN')`，路徑改由設定提供；
  - 把「哪些腳本只能在家中 Windows 跑」列成清單放進文件。

**R3　沒有查詢層，知識不容易拿來用**
- 現象：目標 1 是「作為日後決策的參考」，但現在只能翻 Obsidian，或看入口網推上來的整包圖。hermes-graph 推送的逾時已經放寬到 240 秒，隨著事件增加（1016 筆）會繼續變重。
- 後果：知識越多越難用；入口網要做「某人最近的事」「某案的進度」都得再加 pusher。
- 改進：
  - VPS 上用一個 **SQLite（FTS5）索引**，由確定性程式每晚從 vault 重建（可刪可重建，不是權威來源）：實體表、關係表、全文索引；
  - 先給 HERMES 和 Claude 用（CLI `kb.py query`），再考慮給入口網一個唯讀查詢端點；
  - 不先上向量資料庫：成本與維運都要再評估，FTS 加關係表已經能回答大部分「誰、何時、哪案」的問題。

### 3.4 其他風險與觀察

- **地點不是實體**：美食、旅遊、常去的地方都長不出來。建議新增 `Place` 實體（名稱、座標或地圖連結、類別、別名），L1 只在日記**明確寫出店名或地點**時抽取（同樣用逐字比對閘），美食是 Place 加上狀態。【需決定】這會改 L1 prompt，等於推翻「不抽地點」的既有決定。
- **知識庫健康 4 項已經脫鉤卻仍在計算**：建議停掉 `daily-life-score.py` 的推送，或改算新架構的指標（每日新事件數、L3 落地率、孤兒率）。【需決定】
- **pf-cwh、FitnessForge 的 `/api/public/summary` 不需登入**：建議改成需要一把共享金鑰（header），由 api-server 帶上。這會動到兩個子系統和 api-server 的環境設定，屬於部署變更。【需決定】
- **入口網每次開頁都即時打 NAS 上 3 個 API**：首頁速度受 NAS 影響。建議改成「先回快取並附資料年齡，背景再更新」——快取已經存在（`subsystem_summaries`，每 20 分鐘），現在只拿來當備援。
- **文件漂移**：`pipeline-architecture.md` 的排程表要依 `jobs-index.md` 更新（`jobs-index.md` 是自動產生的，以它為準）。

### 4.6 自建「地點」webapp（類似 pf-cwh）可行性

使用者 2026-10-15：「我其實在vps有架Adventurelog 但感覺用處不大 吃ram又多 這次新增美食地圖 幫我評估自建類似pf-cwh這樣的webapp整合旅遊美食及知識庫地點主題可行性」。

**結論：可行，且比維持 AdventureLog 划算。建議做成「入口網的一個頁面＋api-server 的一組路由」，而不是第六個獨立 webapp。**

**為什麼不另開像 pf-cwh 的獨立 app**：pf-cwh 是 Vite＋Express＋Drizzle＋Postgres＋Google OAuth＋Apache 子路徑（`/pf`）＋獨立容器，維運面很大（登入、session、子路徑、自己的部署流程）。地點資料沒有「別人也要登入」的需求，也沒有獨立的外部資料源要爬。入口網已經有 api-server、Postgres、登入與 `gis-portal`，多一個 app 只會多一份部署與備份。

**資料模型（單一 `places` 表，旅遊與美食共用）**

| 欄位 | 說明 |
|---|---|
| id、name、aliases[] | 名稱與別名（日記裡的叫法） |
| kind | `food` / `sight` / `stay` / `other` |
| status | `want` / `been` / `fav` / `avoid`（美食用全部；旅遊用 want/been） |
| lat、lng、map_url、address_hint | 座標優先從地圖連結解析；沒座標也能列入清單 |
| tags[]、area、rating、must_try、why_want、source | 與 §4.2 日記格式一致 |
| first_seen_at、visited_at、diary_refs[] | 回溯到日記（目標 1：來源可回溯） |
| trip_id（選用） | 旅遊群組，取代 AdventureLog 的 collection |

不需要 PostGIS：個人規模（數百到數千筆）用 `lat/lng` 欄位加前端篩選就夠，「離某點最近」用球面距離公式在 api-server 算即可。

**資料流（知識庫是權威來源）**：日記 → 確定性萃取器（比照 ideas，抽 `### HH:MM 🍜 店名` 與旅遊地點段落，不新增模型呼叫）→ 推送到 api-server `POST /api/places/sync`（冪等，以 name＋日記 id 去重）→ 入口網讀 `GET /api/places`。入口網只讀，要改狀態仍走「複製一句話給 HERMES」（原型已有），保持單向、可回溯。這與現有 ideas 管線同一模式，HERMES 已經會做。

**RAM 比較（估計，未實測）**

| 項目 | AdventureLog（現況） | 自建 |
|---|---|---|
| 組成 | Django＋SvelteKit＋PostGIS＋Memcached（官方 compose 約 4 個容器） | 多一組路由，沿用既有 api-server 容器與 Postgres |
| 常駐 RAM | 約 2 GB（本報告 §4.5 的估計；使用者回報「吃 RAM 多」） | 約 0（路由在既有行程內）；底圖若自架 PMTiles 只是靜態檔 |
| 可以釋放 | 停掉 AdventureLog 的 VPS 實例後釋放該 2 GB | — |

**底圖選型**（要底圖，已決定）

| 方案 | 做法 | 優點 | 缺點 |
|---|---|---|---|
| **A（建議）自架 PMTiles＋MapLibre** | 台灣（或東亞）區域的 PMTiles 單一檔案放在 gis-portal 的靜態目錄，MapLibre GL 以 `pmtiles://` 讀取（nginx 要支援 Range 請求） | 不依賴外部服務、不洩漏你在看哪一區、不吃 RAM、離線可用、無 CSP 外部網域問題 | 檔案約數百 MB 到 GB 等級（**未實測，需要實際下載區域擷取後確認**）；要選樣式（可用 Protomaps 的開源樣式）；字型與圖示要一併自架 |

**不建議做的**：自建行程規劃、預算、協作、ICS 匯出等 AdventureLog 的功能。若用到的是這些，才有理由保留它；使用者說「用處不大」，所以排除。

### 4.9 定位：「美食及旅遊地圖」與「附近」功能（2026-10-15）

使用者原話：「這個新功能我打算定位成美食及旅遊地圖 請幫我確認我希望有個功能是 以我目前的位置為基準 抓出距離由近到遠的有記錄美食或旅遊地點 主要目的是 拿著手機到處走 隨時就知道附近有無想吃美食或想去的地點」。

**結論：可行，前端已做出原型（示範資料）。**

| 需求 | 做法 | 狀態 |
|---|---|---|
| 以目前位置為基準 | 瀏覽器定位（`watchPosition`），按「📍 找附近」才會向使用者要權限；位置只在瀏覽器計算，不送任何伺服器 | 原型完成 |
| 由近到遠 | haversine 球面距離；清單顯示距離與方位（北、東北…）；距離相同以 id 排序 | 原型完成，有單元測試 |
| 有記錄的美食與旅遊 | 同一張 `places`，`kind` 分美食／旅遊；篩選「🍜 美食／🧭 旅遊」；旅遊的 want 顯示成「想去」 | 原型完成 |

**限制（要先知道）**
1. **只有「打開網頁時」才會知道附近有什麼。** 網頁在背景或鎖屏時不能可靠地持續定位，所以做不到「走過去自動跳通知」。要這種體驗需要原生 App，或（較省事）把網頁加到手機主畫面，每次出門前打開一下。
2. **沒有座標的地點算不出距離**，只會在清單上註明「另有 n 個沒座標」。HERMES 盤點顯示約 90 筆舊紀錄只有 1 筆有座標、2 筆有地圖連結，所以**真正有用的「附近」取決於座標補齊**（見 §4.8 的座標方案）。
3. 定位只能在 https 網址使用（入口網在 Caddy 後面是 https，符合）；室內或訊號差時誤差大，畫面會標示誤差，超過 200 m 會提醒。
4. 底圖是第三方圖磚：地圖載入時，瀏覽器會向圖磚服務請求目前檢視範圍的圖磚，等於讓對方知道你在看哪一區（不含精確座標，但開附近模式時地圖會縮放到你所在位置附近）。若在意，改用自架 PMTiles 可避免（§4.6 方案 A）。
5. 驗證：用 Chromium 模擬定位驗證了排序、半徑、移動後更新、藍點與手機版版面；**沒有在真實手機上實測 GPS**，也沒驗證「使用者拒絕定位」的實際提示（無頭瀏覽器不會彈出權限視窗）。
