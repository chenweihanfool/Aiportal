# HERMES ↔ Claude 控制頻道

用一個**獨立的小 repo**（`chenweihanfool/hermes-control-channel`）裡一
個**永遠不會被合併**的長效 PR，當作 HERMES（本機/Synology 端）跟 Claude
session（雲端）之間的雙向留言板。起因：Claude 執行的雲端沙箱對外連線會
經過一個有政策限制的出口代理，連不到 `*.synology.me` 這種個人自架網域
（HERMES 那邊直接連 Claude 也一樣連不到，沒有對應的公開端點），但兩邊
各自都連得到 `github.com`——所以拿 GitHub 當中介，兩邊都只跟 GitHub 對
話，不需要打通彼此的網路。

**這裡的腳本（`poll-control-pr.ps1` 等）本身還是跟著 HERMES 的其他腳本一
起放在這個 Aiportal repo 的 `services/hermes-status/` 底下**，跟
`collect.ps1` 共用同一套部署、同一份 `.env`——只有它們去輪詢/留言的**目
標 PR**，是刻意指到另一個獨立小 repo，不是這個 Aiportal 本體。這樣拆的
理由：
- **PAT 風險隔離**：控制頻道用的 GitHub PAT 只需要能碰一個空殼 repo，外
  洩或設定失手也偷不到正式產品程式碼。
- **PR 列表衛生**：一個永遠不合併、不關閉的 PR 擺在 Aiportal 自己的 PR
  列表裡容易被誤判成該處理掉的東西；獨立 repo 的話，那個「怪 PR」本來就
  是那個 repo 唯一的用途，不會跟正式的 PR 混在一起看。

## 運作方式

```
Claude 推一個 commit 上 master
        │
        ▼（HERMES 排程輪詢 GitHub，不是被動 webhook）
   poll-control-pr.ps1 發現新 commit
        │
        ▼
   HERMES 執行對應動作（Invoke-HermesControlAction，內容待你填）
        │
        ▼（HERMES 呼叫 GitHub API 留言在控制 PR 上）
   在控制 PR 上貼一則留言
        │
        ▼（Claude 已用 subscribe_pr_activity 訂閱這個 PR）
   GitHub webhook 即時推給 Claude session，喚醒它讀留言、接手處理
```

反過來（Claude → HERMES）也是同一個 PR：Claude 直接在 PR 上留言，
`poll-control-pr.ps1` 下次輪詢時讀到，比對留言內容裡有沒有
`Generated by [Claude Code]` 這個 Claude Code 的強制留言簽名（見
`.claude/` 系統規則，每則 Claude 發的留言結尾都會有這個），有就是
Claude 發的、該處理；沒有（含 HERMES 自己貼的）就跳過，避免自己回自己
的留言造成無窮迴圈。

## 為什麼不直接建一個 webhook 讓 HERMES 主動推

Claude Code Remote 平台目前沒有開放「幫任意第三方系統開一個通用 inbound
webhook」這種工具——僅有的 `watch_url` 是綁定給 Anthropic 自己的 Artifact
republish 通知用的，簽名金鑰是封裝給 Artifact 服務用的，HERMES 這種外部
腳本沒辦法用它正確簽章送請求。GitHub PR 留言事件是目前這個環境裡唯一已經
支援、能把「外部事件」即時推進 Claude session 的管道，所以借用它。

## 這個頻道的限制

- **喚醒 Claude 這一段是即時的**（GitHub webhook 推播），但 **HERMES 那
  一段是輪詢**（排程跑 `poll-control-pr.ps1`），延遲取決於你排的輪詢間
  隔，不是雙向即時。
- **訂閱狀態綁在單一 Claude session，不是永久基礎設施**。目前這個 PR 是
  由某個 Claude session 呼叫 `subscribe_pr_activity` 訂閱的，只要那個
  session 還活著就會收到留言事件；如果那個 session 結束、你之後開一個全
  新的 session，新 session 需要重新呼叫一次 `subscribe_pr_activity` 訂閱
  同一個 PR，閉環才會繼續動——不是這個 PR 本身自動永久有效。
- 這個 PR **永遠不要合併、也不要關閉**，只要還在用這個頻道。標題已經標
  `[DO NOT MERGE]`，PR 說明裡也寫明原因，避免之後有人（或未來的 Claude
  session 照慣例）誤把它當成一般 PR 處理掉。

## 設定步驟（HERMES / Synology 端）

1. **建立 GitHub PAT**：GitHub → Settings → Developer settings →
   Personal access tokens → Fine-grained tokens → 新建一個只限
   `chenweihanfool/hermes-control-channel`（不是 Aiportal 本體）這個 repo
   的 token，權限給 **Pull requests: Read and write** 跟 **Issues: Read
   and write**（PR 留言底層走的是 Issues API，兩個都要開）。存起來，不要
   commit 進任何 repo。

2. **填 `.env`**：複製 `services/hermes-status/.env.example` 到同目錄的
   `.env`（跟 collect.ps1 共用同一個 `.env`，已經 gitignore），把下面三
   個新欄位填好：
   - `GITHUB_PAT`：上一步產生的 token
   - `GITHUB_REPO`：`chenweihanfool/hermes-control-channel`（獨立小
     repo，不是 `chenweihanfool/Aiportal`）
   - `CONTROL_PR_NUMBER`：那個獨立 repo 裡控制 PR 的號碼（開這個 PR 的
     Claude session 會直接告訴你）

3. **填 `Invoke-HermesControlAction`**：打開
   `poll-control-pr.ps1`，裡面有一個目前只會寫 log、什麼都不做的
   `Invoke-HermesControlAction` 函式——這是唯一需要你決定「收到訊號後實
   際要做什麼」的地方，其他輪詢/留言/去重的管線都已經接好。

4. **註冊排程**：跑一次 `setup_control_channel_task.ps1`（跟
   `setup_task.ps1` 註冊 `HermesStatusCollector` 同一套模式），會建立一
   個 `HermesControlChannel` 排程任務，預設每 5 分鐘跑一次
   `poll-control-pr.ps1`。

## 留言格式慣例

不強制，但建議：

- HERMES 貼的留言統一加 `[HERMES]` 前綴，方便人類在 PR 頁面上一眼分辨誰
  講的話（Claude 的留言結尾本來就有官方簽名可辨識，不需要額外前綴）。
- 內容盡量講清楚「做了什麼、結果是什麼、需不需要 Claude 接手」，因為
  Claude 端收到的就是這則留言的原始文字，沒有額外上下文。
